# ТЗ: automation_key — прокинуть в requireConsent (все гейтованные инструменты, 5 сервисов)

**Статус:** уточнение владельца 2026-08-11. Реализуется параллельно в calendar-mcp, drive-mcp, sheets-mcp, docs-mcp сейчас; в gmail-mcp — отдельным заходом, как только освободится текущая работа над automation_key (срок/названия/менеджер, те же файлы).

## Контекст

`automation_key` (единая генерация в gmail-mcp, ТЗ `TZ_automation_key_hub.md`)
уже позволяет получить временный/постоянный ключ со scope на нужные
сервисы. Но само владение ключом сейчас никак не проверяется НИ В ОДНОМ
инструменте этих пяти серверов — только в ticktick-mcp (у него отдельная,
уже не связанная с `consent.ts` архитектура). `consent.ts` (портируемый
байт-в-байт файл, общий у gmail/calendar/drive/sheets/docs-mcp) прямо
документирует: «automation_key-ветка... СОЗНАТЕЛЬНО не реализована в этой
версии... YAGNI» — теперь она нужна.

`requireConsent()` — ЕДИНСТВЕННАЯ точка, через которую обязаны проходить
ВСЕ write-инструменты (`gate.md §3.1`). Значит прокидка ключа в
`requireConsent` автоматически покрывает ВСЕ ~60 вызовов сразу по
архитектуре, если сделать её В САМОМ `consent.ts`, а не в каждом
инструменте отдельно логику проверки — но каждый ИНСТРУМЕНТ всё равно
обязан (а) принимать `automation_key` как необязательный параметр схемы,
(б) передавать его в свой вызов `requireConsent`.

## Что менять — `consent.ts` (одна логика, портируется во все 5 репо)

### 1. Новые поля `RequireConsentParams<T>`

```ts
/** Automation_key, присланный вызывающим (headless-автоматика). undefined/"" — обычный человеческий путь, ничего не меняется. */
automationKey?: string;
/** DI: проверяет ключ на предмет "покрывает ли он МЕНЯ (этот сервис) прямо сейчас". Undefined ⇒ ветка automation_key целиком выключена — побайтовое поведение как раньше. */
checkAutomationKey?: (key: string) => Promise<{ ok: boolean; channel?: string }>;
```

### 2. Ветка в начале `requireConsent` — ДО проверки `hasId !== hasReply`

Если `automationKey` присланный (непустой) И `checkAutomationKey` задан
(DI-функция подключена сервером):

1. Зовём `checkAutomationKey(automationKey)`.
2. Если `{ok: false}` — **НЕ ошибка, тихий fallthrough** на обычный
   plan/execute путь (тот же принцип, что уже в ticktick-mcp: неверный/
   просроченный/не-по-scope ключ не блокирует — просто не даёт бонуса,
   вызывающий продолжает как обычный человек с `user_reply`). Тот же
   принцип нужен на случай, если модель "угадывает"/подставляет мусор в
   параметр — не должна получить внятную ошибку, которая подскажет, что
   параметр вообще существует и стоит перебирать.
3. Если `{ok: true, channel}` — строим план (`plan()`), проверяем предел
   батча (`cfg.sendBatchMax`, та же проверка, что в обычной фазе плана),
   ЗАТЕМ вызываем `rehash(built.addressing)` и сравниваем с
   `built.objectHash` — **тот же binding-чек, что в обычном исполнении**
   (не пропускать: даже автоматике нельзя исполнить план, для которого мир
   уже уехал между построением плана и этой же секундой — редкий, но
   реальный случай гонки). Совпало — исполняем немедленно: пишем аудит-
   запись (`store.appendConsentAudit`) с `actor: "automation"`,
   `checks: {automationKey: channel ?? "unknown"}`, `outcome: "confirmed"`,
   возвращаем `{kind: "confirmed", manifestId: "", payload: built.payload, auditId}`
   (`manifestId` пустой — манифест в `mcp_manifests`/`consent_manifests`
   не создавался вовсе, это прямой путь, не план→ожидание). Рассинхрон
   (`rehash` не совпал) — `refuse(...)`, тот же текст/механизм, что и у
   обычного binding-провала в фазе исполнения ниже по файлу (посмотри его
   и используй ту же формулировку, не изобретай новую).

### 3. Обратная совместимость

`checkAutomationKey` не задан (сервер его не подключил) → automation_key-
ветка целиком не существует, поведение побайтово как до этой правки. Это
единственный способ, которым `consent.ts` остаётся переносимым модулем без
runtime-импорта конкретной реализации проверки ключа (та живёт в
`automation_key.ts`/store каждого сервера — DI, не прямой импорт).

## Что менять — КАЖДЫЙ инструмент (все ~60 вызовов `requireConsent<...>({...})`)

1. Найди КАЖДЫЙ вызов `requireConsent<...>({` в `src/tools/*.ts` (используй
   `grep -rn "requireConsent<" src/`, посчитай — знай точное число ДО
   правки и сверь после, чтобы ничего не пропустить).
2. У КАЖДОГО инструмента, который эти вызовы оборачивают — добавь в его
   Zod-схему параметров необязательное поле:
   ```ts
   automation_key: z.string().optional().describe(
     "For headless automation only — a valid automation_key skips the " +
     "human confirmation step entirely. Humans and interactive assistants " +
     "must NEVER guess or fabricate a value here; leave it unset."
   )
   ```
   (текст описания — важен, тот же дух, что уже стоит в ticktick-mcp у
   аналогичного параметра — "не угадывать, оставить пустым, если не
   настоящая автоматика").
3. В самом вызове `requireConsent<...>({...})` — добавь
   `automationKey: args.automation_key, checkAutomationKey` (последнее —
   пробрасывается сверху, из того же места, откуда сейчас пробрасывается
   `store`/`cfg`/`tg` — найди, ГДЕ в `server.ts` собираются общие
   зависимости для тулов, туда же подключи DI-функцию проверки ключа).

## Что менять — сервер (`server.ts`/аналог, DI-подключение)

Реализуй `checkAutomationKey` для ЭТОГО сервиса — сверяет присланный ключ:
1. Со статическим `AUTOMATION_KEY` (если у сервиса он есть — читай, как
   это уже сделано, если сделано; если нет — просто не будет канала
   "static", только "window").
2. С активными окнами в общей таблице `tg_automation_windows`
   (`CONSENT_DATABASE_URL`, та же база, где уже живут `consent_manifests`/
   `tg_approvals`) — окно валидно для МЕНЯ, если `revoked_at IS NULL AND
   (expires_at IS NULL OR expires_at > now) AND (scope = 'all' OR
   '<имя_этого_сервиса>' входит в scope, разбитый по запятой)`. Канонические
   имена сервисов: gmail/calendar/drive/sheets/docs/ticktick.

Если у сервиса ЕЩЁ НЕТ подключения к этой таблице (кроме gmail-mcp, где
она уже есть как источник для генерации) — подключить ЧТЕНИЕ (не запись:
генерация остаётся только в gmail-mcp) той же таблицы, тот же `CONSENT_
DATABASE_URL`, что уже используется для `consent_manifests`/`tg_approvals`
в этом сервисе.

## Тестовый план (на каждый из пяти сервисов)

1. `checkAutomationKey` не задан (DI-функция undefined) — `requireConsent`
   ведёт себя ПОБАЙТОВО как раньше на существующих тестах (регресс-тест —
   просто прогнать существующий набор `scripts/test-consent.mjs` без
   изменений, всё зелёное).
2. Валидный `automation_key` (заглушка DI возвращает `{ok:true}`) —
   исполнение происходит С ПЕРВОГО вызова, без `manifest_id`/`user_reply`.
3. Невалидный/просроченный ключ — тихий fallthrough на обычный план (НЕ
   ошибка, НЕ подсказка, что параметр вообще был проверен).
4. Binding-чек (`rehash`) всё ещё срабатывает на automation-пути — тест,
   где `rehash` возвращает ДРУГОЙ хеш, чем `plan()` — ожидается отказ, не
   тихое исполнение рассинхронизированного плана.
5. Превышение `cfg.sendBatchMax` на automation-пути — тот же отказ, что и
   на обычном плановом пути.
6. Аудит-запись при automation-исполнении несёт `actor: "automation"` и
   `checks.automationKey` с меткой канала.
7. Хотя бы один живой инструмент этого сервиса (не только юнит-тест
   `consent.ts` в изоляции) — принимает `automation_key` в схеме, реально
   передаёт его в `requireConsent`, полный прогон через мок-DI подтверждает
   бай-пас на уровне ИНСТРУМЕНТА, не только ядра гейта.
8. Регресс — полный `npm test` этого репозитория зелёный, ничего старого
   не сломано (если тесты ссылаются на старую сигнатуру `requireConsent` —
   не подгонка, обнови под новый контракт, раз он расширяет, а не убирает
   старое).

## Явно НЕ входит

- gmail-mcp — отдельный заход (те же файлы заняты параллельной правкой
  срока/названий automation_key).
- ticktick-mcp — уже реализовано отдельной, несвязанной архитектурой.
- Смена дефолтного поведения БЕЗ ключа — человеческий путь (`manifest_id`+
  `user_reply`) не трогается ни на бит.
